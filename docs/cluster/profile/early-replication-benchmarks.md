## flush 段边界与入队任期

组按当前日志段容量截取就绪队列的连续前缀，维持 FIFO，并在取批时拒绝旧任期入队的写。改前版 `71080870a731…` 已支持同连接 SET 提前提交，改后版 `5978ec01ba18…` 加入段边界和任期检查。该阶段将异步 I/O 和 drain 改为默认开启，两版在本轮均显式开启。 [SET 提前提交实验](../io_uring.md#同连接-set-提交与确认解耦)

2026-11-23 在 `172.31.23.2`（Ubuntu 26.04、i7-13700KF、NVMe ext4）测量未插桩的 Folly Release。每轮共 256 MiB，256 KiB/value，使用不同 key，预热 64 笔并静置 5 秒。每个连接发出 64 笔再收齐回复。三副本停一台，从首笔 SET 发出计时，直到所有原写连接 `WAIT 1` 成功。原 cluster 使用改后版同一二进制，表中吞吐为三轮中位数，单位 MiB/s。

| 连接数 | 改前 Raft | 改后 Raft | 变化 | 原 cluster |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 162.22 | 169.08 | +4.2% | 623.66 |
| 2 | 180.47 | 179.86 | −0.3% | 634.36 |
| 8 | 191.11 | 195.75 | +2.4% | 652.86 |

- 2、8 连接的三轮范围重叠。8 连接仅计 SET 回复的吞吐提高 0.2%，批次 P95 略升。末尾 WAIT 的重查时机也影响确认吞吐。原 cluster 的 WAIT 确认副本应用，`raft.flush` 的 SET 还须等多数落盘。
- 27 轮均通过原写连接 `WAIT 1`、离线副本重启后的 `WAIT 2` 和全部 1088 个值读回。该轮没有刻意跨越 1 GiB 段边界，也没有重新统计刷盘次数，无法单独量化段截取的收益。
- 当时仍有票据容量、WAL 排空和 worker 等待应用等成本。后续用初始火焰图与 Trace 定位复制、编码和应用等待。 [v3 基线与诊断](v3-baseline.md)

## CRC 指令优化

独立试验每轮写入 256 MiB，每连接一笔 SET 在途。1、8 连接的 SET 吞吐分别提高 **8.5%**、**4.3%**。计时终点为 SET 回复，pipeline 对照还包含批末 `WAIT 1`。该试验未合入，提交阻塞仍存在。
