# v12 Fetch records 分散发送（收益待确认，暂回退）

Leader 按同一 schema 编码协议字段，通过 iovec 直接发送响应持有的 records，省去 records → 完整帧的一次复制。响应保留到发送完成或失败；最多 32 个 records 分片，超限用连续编码。Follower 解码未改。

## 实验结果

Raft memory、1 连接、pipeline 64、256 MiB、256 KiB/value，吞吐包含原写连接的 `WAIT 1`。只测本轮三次，上一轮引用 v10 归档。 [平台总览](http://127.0.0.1:8787/#/v12/overview) · [运行记录](http://127.0.0.1:8787/#/v12/runs)

| 指标 | v10 | v12 | 变化 |
| --- | ---: | ---: | ---: |
| 吞吐中位数（MiB/s） | 460.88 | 464.05 | +0.7% |
| 吞吐算术均值（MiB/s） | 447.47 | 399.61 | −10.7% |
| 批次 P95 中位数（ms） | 44.01 | 48.90 | +11.1% |

三轮吞吐 **467.87 / 266.90 / 464.05 MiB/s**，P95 **41.70 / 93.49 / 48.90 ms**。均值下降主要由第二轮造成，另两轮吞吐略高于 v10 中位数，有小幅收益迹象。P95 一轮改善、一轮变差，不能据此认定方案导致退化，也不能删除慢轮后宣称稳定提升。

第二轮 SET 阶段 **958.84 ms**，第一、三轮为 **547.01 / 551.45 ms**；末尾 WAIT 分别 **0.15 / 0.30 / 0.21 ms**，慢点发生在 SET 阶段。第二轮副本重启追赶也较慢（**3007.01 ms**，另两轮 **702.81 / 601.09 ms**），该恢复阶段不计入吞吐。正式轮没有 Trace 或主机调度采样，现有记录不足以确认慢因；独立诊断不能替代第二轮证据。

## 独立诊断与结论

Leader CPU **510 → 470 ms（−7.8%）**，memcpy 叶子样本 **87 → 72**；Follower CPU **256 → 266 ms**。同样 1024 笔写的 WAL 提交 **153 → 176 次**，worker 排队区间并集 **211.95 → 265.10 ms**。各区间会重叠，单次采样不能证明因果。 [火焰图](http://127.0.0.1:8787/#/v12/flamegraphs) · [Trace](http://127.0.0.1:8787/#/v12/trace)

**收益与慢轮原因待确认，代码暂回退至 v10。** 保留候选补丁和二进制，后续先核实慢轮与合批节奏，不将 CPU 热点下降直接等同于吞吐提升。Follower 借用解码方案尚未测试。

Debug、Release、ASAN+UBSAN 各 25 项协议/网络单测通过，覆盖 Java golden、null/empty、大 records、多分片及超限回退、输出不变、8 MiB 发送与断连重连；flush/memory 两项 pipeline 回归通过。平台另完成 29 项单测、一项集成回归、三轮正确性验证和独立诊断。首次平台构建发现 v11 回退遗留的测试目标文件，核对源码并重编译后续跑成功，没有追加 benchmark 轮次。
