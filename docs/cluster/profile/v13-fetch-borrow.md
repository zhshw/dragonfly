# v13 Follower Fetch records 借用解码

**保留实现。** 大 Fetch 解码时，records 直接借用不可变接收缓冲，并将所有权传给有界 effect 缓存，省去一次 records 复制。按整个分配容量计费，连接复用或断开不影响已借用数据；小响应沿用复制路径，CRC 校验与提交、应用顺序不变。基于 v10，不包含 v11/v12 改动。

## 实验结果

Raft memory、1 连接、pipeline 64、256 MiB、256 KiB/value，计时包含原写连接 `WAIT 1`。通过 `profile run -id v13` 只测本轮三次，上一轮引用 v10 归档。 [平台总览](http://127.0.0.1:8787/#/v13/overview) · [运行记录](http://127.0.0.1:8787/#/v13/runs)

| 指标 | v10 | v13 | 变化 |
| --- | ---: | ---: | ---: |
| 吞吐中位数（MiB/s） | 460.88 | 486.54 | +5.6% |
| 吞吐算术均值（MiB/s） | 447.47 | 470.84 | +5.2% |
| 批次 P95 中位数（ms） | 44.01 | 45.25 | +2.8% |
| 批次 P95 算术均值（ms） | 44.03 | 48.68 | +10.6% |

三轮吞吐 **438.43 / 487.56 / 486.54 MiB/s**，P95 **58.41 / 42.37 / 45.25 ms**。第一轮末尾 WAIT 为 **7.88 ms**，另两轮均为 **0.14 ms**；WAIT 不在批次 P95 的计时中，不能用于解释第一轮批次尾延迟。吞吐均值和中位数均有收益，P95 未改善；这是三轮跨轮对照，尚未验证其他负载。

## 独立诊断与结论

- Follower CPU **256 → 200 ms（−21.9%）**，memcpy 叶子样本 **36 → 20**，峰值 RSS **411.02 → 407.52 MiB**。1024 笔写全部命中接收缓存，没有因共享整个缓冲而退回 WAL 重放。
- Leader CPU **510 → 506 ms**；WAL 提交 **153 → 176 次**，worker 排队区间并集 **211.95 → 263.28 ms**。Follower 复制减少后，Leader 排队和逐笔应用仍需分析，各阶段区间不能相加。

**保留这次吞吐优化，明确尾延迟未获益。** 单次独立诊断支持复制开销下降，不能解释正式第一轮的慢因，也不能把全部 CPU/RSS 差异归因于本改动。 [火焰图](http://127.0.0.1:8787/#/v13/flamegraphs) · [Trace](http://127.0.0.1:8787/#/v13/trace)

Debug、Release、ASAN+UBSAN 各 **61 项单测**通过，覆盖协议输出、借用生命周期、连接复用与断开、CRC 拒绝、截断和缓存预算/释放；flush/memory pipeline、落后副本快照恢复 **3 项集成回归**通过。平台另完成 **29 项单测、1 项集成回归**，三轮均通过副本确认、恢复与全量读回，独立诊断的 **2150 条观测**已在 Langfuse 核验。

## Trace 复核

复用本轮时间线和 CPU 栈，未重跑 benchmark。区间交集表示时间重叠，不能直接当作因果或可节省时间。

- Leader worker 排队 **263.28 ms**：与 apply 重叠 **153.53 ms（58.3%）**、编码 **61.72 ms（23.4%）**、追加准备 **30.31 ms（11.5%）**，三者之外 **17.73 ms**。应用是主要重叠项。
- Follower Fetch RPC **329.19 ms**：与上述 Leader 三阶段分别重叠 **69.44 / 73.90 / 33.86 ms**，合计 **177.20 ms**。Leader 在处理 Fetch 前可经 `Tick()` 执行 apply；RPC 包含等待响应，不能全归为网络或复制。Follower 接收追加 **75.13 ms**、apply **88.33 ms** 均不与自身 RPC 重叠。
- Leader apply **159.61 ms** 中，owner 批执行 **138.23 ms**，其中逐笔 `journal.apply` **137.53 ms**；另有 owner 排队 **10.41 ms**。火焰图中 SET 写入 `LargeString` 的复制占 **24 / 253** 样本，shard 合批仍需保留这部分数据写入。Fetch 完整帧复制为 **16 / 253** 样本，日志读取缓冲清零为 **8 / 253**，仍有局部优化空间。
- 1024 个确认全部匹配到 124 次 apply。应用后确认 P95 **0.744 ms**；16 个 pipeline 批尾额外等待最大 **95.3 µs**、合计 **0.604 ms**，票据完成暂列备选。

**P0-2 值得评估，但最大收益尚未证实。** 下一步应把逐笔 SET 的 shard 投递、等待和执行分开计时，再决定合批范围。复核程序和结果保存在该执行目录的 `trace-review/`。
