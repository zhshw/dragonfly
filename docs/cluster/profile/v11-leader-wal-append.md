# v11 Leader WAL 追加复用编码结果（已回退）

本地 SET 编码器把不可变字节和批次边界一起交给同段异步追加。追加核对任期、连续 offset 和段容量，复用编码时的 CRC 结果。

## 实验结果

Raft memory、1 连接、pipeline 64、256 MiB，吞吐包含原写连接的 `WAIT 1`。正式指标取三轮中位数，以 v10 归档为上一轮。 [平台总览](http://127.0.0.1:8787/#/v11/overview) · [运行记录](http://127.0.0.1:8787/#/v11/runs)

| 指标 | v10 | v11 | 变化 |
| --- | ---: | ---: | ---: |
| 吞吐（MiB/s） | 460.88 | 459.58 | −0.3% |
| 批次 P95（ms） | 44.01 | 52.40 | +19.1% |

## 诊断与结论

快路径消除了 Leader WAL 追加阶段的第二遍 CRC，该阶段的 CRC 样本从 **24 降到 0**，Leader CPU 从 **1.99 降到 1.90 ms/MiB**。WAL 追加准备区间并集从 **41.95 降到 0.99 ms**。同为 1024 笔写，drain 提交从 **153 增至 177 次**，平均合批从 **6.69 降至 5.79 笔**，worker 排队区间并集从 **211.95 增至 213.22 ms**。各阶段区间有重叠，应分别解读。 [火焰图](http://127.0.0.1:8787/#/v11/flamegraphs) · [Trace](http://127.0.0.1:8787/#/v11/trace)

正式吞吐降幅小于轮间波动，三轮的批次 P95 都高于 v10，因此回退 C++ 快路径。追加准备缩短可能改变 drain 收集窗口，现有证据来自单次诊断。复试前先核实合批变小的原因，同时检查批大小、提交次数、worker 排队和端到端 P95，以正式吞吐和 P95 判断 CRC 或 `memcpy` 热点变化是否有实际收益。

## 验证与构建修复

Ubuntu 上 71 项相关单测通过，覆盖同段追加、CRC 拒绝、短写和恢复。平台验证与归档完成。

首次 Release 构建和三轮 benchmark 成功，诊断副本仍对新批次对象调用字符串的 `.size()`，导致编译失败。插桩改用编码阶段算出的 `records_size` 后，第二次执行完整跑通并入库。两次用的是同一 Release 二进制，原始记录及候选补丁保存在 v11 执行目录。
